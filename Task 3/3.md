## 3.1 Structures compared

| Structure | Description | Reliability | Performance | Ease of updating |
|---|---|---|---|---|
| Simple (monolithic) | All OS services in one kernel address space (MS-DOS style simple; classic Unix/Linux monolithic) | Low: one faulty driver can crash the kernel | High: a service is a function call / one system call | Hard: rebuild/restart kernel |
| Layered | OS built in layers 0..N; each layer uses only the layer below | Good (easy to verify) | Lower: each request may cross many layers | Good: replace a layer |
| Microkernel | Tiny kernel (scheduling, IPC, memory); file systems, drivers and network run as user-space servers | Highest: a failed server is restarted | Lower: message passing and context switches | Easy: restart/replace a server without reboot |
| Modular (loadable kernel modules) | Monolithic core with modules loaded at run time | Medium (modules run in kernel mode) | High | Good: load/unload modules without reboot |
| Hybrid | Mixes approaches (microkernel-like design plus some services in kernel) | Medium to high | Medium to high | Good |

## 3.2 How real systems are structured

| System | Structure |
|---|---|
| Linux | Monolithic kernel with loadable kernel modules (modular); drivers, file systems and network stack run in kernel mode |
| Windows | Hybrid: executive and kernel with a hardware abstraction layer; many services in kernel mode, some subsystems in user mode |
| Android | Layered stack on a Linux kernel: kernel, hardware abstraction layer, native libraries and runtime (ART), application framework, apps; each app in its own sandbox |
| FreeRTOS | Very small library-style kernel (scheduler, queues, semaphores, timers) linked with the application in one address space; optional memory-protection unit (MPU) variant |
| QNX Neutrino | True microkernel: only scheduling, IPC, interrupt handling and basic memory in the kernel; drivers, file systems and networking are user-space processes; POSIX real-time |

## 3.3 Defended choices (two environments)

**Patient monitor – microkernel (QNX-style) RTOS.**
Monitors run for years and drive life-critical alarms. In a microkernel the sensor driver, display driver and network stack are separate processes with their own address spaces: if the display driver fails, it is restarted while the alarm task keeps running. The kernel is small, so it can be verified and its worst-case latency analysed. Priority-based pre-emptive scheduling with priority inheritance gives the bounded alarm response. A resource-constrained variant (FreeRTOS with MPU) is acceptable when cost or memory dominate.

**Database server – modular monolithic kernel (Linux).**
Throughput and mature file-system, networking and storage drivers matter most. The database performs many system calls per second, so the cost of one trap should be minimal. Loadable modules allow driver updates without rebooting, and fail-over covers kernel crashes. Reliability comes from the cluster (Task 2), not from the kernel structure.

## Alternative Concept and Complexity Analysis – monolithic kernel for the bedside monitors

**Solution if used:** the monitor runs a monolithic kernel in which drivers, network stack and file system are kernel code.

| Criterion | Microkernel | Monolithic |
|---|---|---|
| Time cost of one service request | Client -> kernel IPC -> server -> kernel IPC -> client: 2 messages and at least 2 context switches. t about 2 x t_ipc + 2 x t_ctx; if a request passes through m servers, O(m) messages. Typically about 1 to 5 microseconds (estimate, not measured). | One trap into the kernel and a function call: t about t_syscall. Measured on my Linux test machine: about 100 ns per system call (Task 6). O(1). |
| Memory taken by the kernel | Kernel image tens of KB to about 100 KB (illustrative); servers are separate and loaded only when needed | Kernel image typically several MB to tens of MB plus all built-in drivers (Linux) |
| Effect of a faulty driver | The server process dies; the OS restarts it; other tasks including the alarm continue | The driver runs in kernel mode and can corrupt kernel memory: a kernel panic stops the whole monitor, including alarms |

**Evaluation:** a service request is a few microseconds slower with a microkernel, which is negligible against a 10 ms deadline (a margin of at least 2,000 times). The fault isolation is worth far more than the speed saved, so the microkernel is retained for the monitors.

## Comparison against the hospital's requirements (summary)

| Structure | Monitor (hard real-time, never crash) | Database server (throughput, many I/O calls) |
|---|---|---|
| Monolithic | Poor: a driver fault kills the alarm | Good: fastest request path |
| Layered | Fair: verifiable but slower | Fair |
| Microkernel | **Best (chosen)**: isolation, small, analysable timing | Fair: IPC overhead on every I/O |
| Modular | Poor: modules still run in kernel mode | **Best (chosen)**: speed plus updates without reboot |
| Hybrid | Fair | Good |

*Kernel sizes and IPC times are typical or estimated values, not measurements made in this assignment; only the system-call time (about 100 ns) was measured.*
