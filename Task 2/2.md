## 2.1 Comparison of OS types

| Type | Main characteristics | Hospital relevance |
|---|---|---|
| Mainframe | Batch + transaction processing, very high I/O and reliability, hot-swappable hardware | Concepts reused in E4 (high availability, transaction processing) |
| Desktop | Single user, GUI, responsiveness, many apps | E3 workstations |
| Multiprocessor (parallel) | Several CPUs sharing memory/bus; SMP or AMP | E5 imaging server |
| Distributed | Machines connected by a network cooperate; no shared memory; message passing | E6 partner link, later the 3-hospital group |
| Clustered | Several nodes share storage and monitor each other; fail-over, load sharing | E4 database server |
| Hard real-time | Deadline is a guarantee; missing it is failure; no virtual-memory delays | E1 monitors |
| Soft real-time | Deadline is a goal; occasional misses degrade quality | Video/UI on E2, E3; not for alarms |
| Handheld | Small memory, slow CPU, battery, touch screen, wireless | E2 tablets |

## 2.2 Choice for each environment, with rejected alternatives

| Env. | Chosen type | Rejected alternatives and reasons |
|---|---|---|
| E1 Monitor | **Hard real-time** embedded OS (microkernel RTOS) | Soft RT / desktop: no guaranteed 10 ms. Handheld: designed for power, not deadlines. Distributed: network delay is unbounded. |
| E2 Tablet | **Handheld** OS | Desktop: too much memory/storage, poor battery life. RTOS: no app ecosystem or UI stack. |
| E3 Workstation | **Desktop** (multitasking, GUI) | Handheld: limited multitasking/peripherals. RTOS: no desktop software support. |
| E4 Database | **Clustered** (2+ nodes, shared storage/replication, fail-over) | Single big multiprocessor: single point of failure (see below). Desktop OS: not server-grade. |
| E5 Imaging | **Symmetric multiprocessor** server (batch-style job queue) | Asymmetric MP: master CPU becomes a bottleneck. Cluster: needs data movement. Single CPU: too slow. |
| E6 Partner link | **Distributed system** (authenticated message passing / RPC / replication) | Shared memory is impossible between sites; a single machine cannot span organisations. |

## 2.3 Symmetric vs asymmetric multiprocessing for the imaging server

| Aspect | SMP | AMP |
|---|---|---|
| Organisation | All CPUs run the same OS and can run any task | A master CPU runs the OS; slave CPUs run assigned tasks |
| Load balance | Dynamic: any CPU takes the next image slice | Master assigns; master can become the bottleneck |
| Failure | Loss of one CPU reduces capacity only | Master failure stops everything |
| Complexity | Needs locking of shared kernel data | Simpler kernel |

**Decision: SMP.** MRI reconstruction splits well into independent slices; any free CPU can process any slice, so utilisation is best and the OS keeps running if one CPU fails. Locking overhead is acceptable for coarse-grained work.

## 2.4 Clustered database server with fail-over

Two or more nodes serve one database. A heartbeat between nodes detects failure, and the surviving node takes over the shared storage/replica and the service address within seconds. Rolling updates are possible: update the standby, fail over, then update the former primary. This meets "must never stop, even during updates".

## Alternative Concept and Complexity Analysis – one large multiprocessor instead of a cluster

**Solution if used:** a single large shared-memory machine (for example 64 processors and a large memory) runs the database.

**Availability.** A = MTBF / (MTBF + MTTR). Illustrative assumptions (not measured): MTBF = 5,000 h, repair/restore time = 4 h.

| Design | Calculation | Result |
|---|---|---|
| Single machine | A = 5000 / 5004 = 0.9992 | About 99.92 %, about 7 h downtime per year; single point of failure; updates need a restart |
| 2-node cluster, fail-over 30 s | Primary failures about 8760/5000 = 1.75 per year x 30 s = about 53 s; both nodes down together about (0.0008)^2 = 6.4 x 10^-7, about 20 s per year | About 99.9998 %, roughly 1 to 1.5 minutes downtime per year; updates by rolling restart |

| Criterion | Cluster of smaller machines | One large multiprocessor |
|---|---|---|
| Cost | Several commodity servers: cost grows roughly linearly with nodes, plus shared storage | Large SMP hardware is priced super-linearly (specialised interconnect, memory); expensive to duplicate |
| Throughput vs number of processors N (time) | Scales by adding nodes; limited by synchronisation/replication overhead | Amdahl's law: S = 1 / ((1 - p) + p/N). With parallel fraction p = 0.95: N = 16 gives 9.1; N = 64 gives 15.4; limit = 20. Lock contention makes it worse. |
| Memory (space) | Each node has its own memory; data partitioned or replicated: total memory is the sum, but each query sees only its node's part/cache | One large single address space (for example TBs) simplifies buffer caching, but the memory is itself a single failure domain |
| Asymptotic | Capacity O(nodes); availability improves with redundancy | Capacity O(N) at best, sub-linear in practice; availability fixed by one machine |

*MTBF, repair time and hardware figures are illustrative assumptions, not measurements.*

**Evaluation:** the cluster is chosen because the stated requirement is availability, not maximum single-machine speed.
